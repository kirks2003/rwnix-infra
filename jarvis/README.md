# Jarvis web assistant

Multi-user browser Jarvis for Chrome desktop and Android Chrome.

## What it does

- Shows every stage in the web UI: boot, wake listening, wake detected, recording, 1.5 s silence stop, Whisper upload, LLM prompt, TTS speaking, errors, and backend request details.
- **Animation preview** buttons switch the core and waveform between every pipeline animation (Standby, Wake, Recording, Transcribing, Thinking, Speaking, Error) without arming; they are disabled while a session runs, so the live pipeline always owns the core.
- Uses self-hosted Whisper wake probes for the phrase `Hey Rocky`; browser speech recognition is not used for wake or prompt STT.
- Captures mono PCM continuously with an `AudioWorklet` while armed. Overlapping voice probes are encoded as complete WAV files, without gaps while Whisper responds.
- Probes fire on the trailing edge of speech, about 350 ms after the talker stops, rather than on a fixed interval. A window that ends mid-word comes back from Whisper empty, which used to cost a whole probe cycle before the wake phrase was heard. Settled probes overlap the previous window by 2 s so a phrase crossing the boundary is not lost. If speech runs on without pausing, a probe is sent anyway once the burst reaches 3 s; that cap counts speech, not wall time, so leading silence cannot trip it mid-word. A forced probe covers everything since the last probe, so on a microphone that never settles a short wake phrase cannot fall into the gap between probes.
- After wake detection, waits for the utterance to finish and sends its complete audio to Whisper. This preserves commands spoken immediately after "Hey Rocky". A wake word alone opens a separate command window with an audible beep. If the completed utterance or the post-beep window comes back empty (the command was spoken but transcription lost it), Jarvis logs it and returns to wake listening without a dead-end error, so the next attempt retries.
- **Silence stop slider.** The **Silence stop** slider in the Mic level panel sets how long the microphone must stay quiet before a recorded command is sent to Whisper: 100 ms to 5 s in 50 ms steps. The server default (`SILENCE_MS`) is only the initial value; the slider applies live — even mid-recording, because the VAD reads the current value on every 100 ms tick — and is saved per browser (local storage), like the wake word. The green silence bar's scale, the pipeline's vad step name ("Stop after 1.5 s silence") and the status-line countdown all follow the slider.
- **Bounded step retries.** If a pipeline step that can be repeated without new input fails — a wake probe or command transcription (the audio is still in the capture buffer), the brain request (the prompt is captured), or the speech output (the answer text is known) — it is retried up to 3 times, 1 s apart, with the already-captured material. The Live log records every attempt (`wake probe failed (attempt 1/3): …; retrying in 1000 ms`) and the pipeline status line shows the next retry. Only after all 3 attempts fail does the pipeline show the usual red error stage and return to wake listening; aborts (Stop, tab hidden) are never retried. This is what keeps a transient Whisper/brain/TTS blip from making the user speak the input again.
- **Audible pipeline beeps** (all from the capture microphone's audio context): the 880→1320 Hz sweep says "wake word heard / speak now"; a soft 660 Hz tick (`probeBeep`) sounds the moment a wake-probe window is sent to Whisper; a higher 1760 Hz ping (`sentBeep`) sounds the moment the command audio is sent and transcription starts — so every upload is audible even on a muted-looking UI.
- Sends audio to one or more self-hosted Whisper endpoints through the backend, so the browser never needs cross-origin access to Whisper.
- Sends the recognized prompt to an OpenAI-compatible self-hosted brain through the backend, so API keys never reach the browser.
- **Endpoint selectors.** The controls panel has two saved per-browser dropdowns: **AI API endpoint** (OVHcloud, OpenRouter, Claude Code, A1 Qwen or A1 DeepSeek, populated from the local opencode/Kandev profile config when readable) and **Whisper server** (`gpu-1`, `vm103 on pve103` or OVHcloud `whisper-large-v3`). Changes apply to the next brain request or transcription request; in-flight calls are not moved.
- Speaks the answer with the selected voice and writes both prompt and answer on the page. **Browser voice** uses `speechSynthesis`; **HAL 9000** uses a self-hosted neural TTS backend through the server proxy.
- Shows a live circular waveform ring around the core: 60 spectrum bars read from a tap on the existing Web Audio graphs (microphone while listening, the shaped HAL output while speaking) with fast-attack/slow-release smoothing and a white flash on hot bars. Stages without a tappable source (browser `speechSynthesis`, Whisper/brain waiting) show deterministic synthetic motion, and the reactor's glow and size follow the overall level.
- **One switch per MCP server** in the controls row (per browser, like the wake word): the backend advertises its MCP servers in `/api/config` (`mcpServers`), the UI builds one on/off switch for each, and every `/api/chat` request carries the enabled set as `mcp: { id: true }`. Today that is the **Web search** switch: when on, the backend runs the `mcp/websearch.mjs` Model Context Protocol server (stdio, no API key) with **three tools**. The backend first runs `web_search` over the user's prompt and hands the results to the brain as context for that one prompt — it queries every free keyless engine **in parallel** and merges the results round-robin, deduplicated by URL, each tagged with its source engine: **DuckDuckGo** (HTML endpoint, ad and redirect links unwrapped), **Bing** (HTML endpoint, `bing.com/ck/a` redirects unwrapped to the real target), **Wikipedia** (search API) and the **DuckDuckGo Instant Answer API** (abstract/definition/direct answer plus related topics, prepended as an "instant answer" block — the closest free thing to an AI answer). In addition the brain gets **both tools as callable functions** (the same tool loop as the knowledge graph, shared five-round budget): it can call `web_search` with its own queries and — for any "latest news" question, including the user's interests (from the knowledge graph or the conversation) — `web_news` with a concrete topic (e.g. "Home Assistant") or one of the interest areas **technik, it, finance, geek, nerd**. `web_news` pulls the latest news (past 7 days) from free keyless sources: **Bing News RSS** as the primary search (its `apiclick.aspx` links are HTTP redirects, resolved server-side to the real article URL), the curated interest feeds (**heise/Golem** = technik, **Ars Technica/The Verge/TechCrunch** = it, **CNBC/MarketWatch/Financial Times** = finance, **Hacker News/Lobsters** = geek, **r/programming + Hacker News + Lobsters** = nerd), and **Google News RSS** as a breadth backup for free topics only (its links are JS-only wrappers, so it only fills slots the primary sources left empty). The third tool, `web_fetch`, opens a **specific URL in a real headless Chromium browser** — a genuine human-browser fingerprint (the real TLS/HTTP2 stack plus JavaScript execution, not a spoofed header set) — and hands the rendered page text to the brain. That is what makes "pull the price from Google Finance" actually work: the quote loads in a post-load XHR, so only a browser that runs the page's JavaScript sees it (a plain HTTP fetch gets the page shell but no live price). The MCP server keeps **one persistent browser per process** (launched lazily on the first fetch, closed on exit), uses a fresh isolated context per fetch (locale follows the answer language), waits for `domcontentloaded` (10 s hard cap) then the `load` event and a bounded network-idle settle so post-load XHRs land, and reads the rendered `innerText` (visible text, reading order, capped at 12 000 chars / 30 000 max). If the browser is unavailable (not installed, crashed, no system libraries) it degrades to a plain browser-header fetch and marks the result `[fetched without JavaScript]`. Because the brain is prompt-injectable, `web_fetch` is SSRF-guarded like the graph is owner-scoped: http/https only, default ports 80/443, no embedded credentials, and private/loopback/link-local/CGNAT/benchmarking IPs are blocked — both as URL literals and against the **DNS-resolved** addresses (so a hostname that rebinds to `169.254.169.254` or the Neo4j container is refused), meaning the brain can reach the public web as a human but never the internal network (cloud metadata, the DB, the app itself). The answer language is injected by the backend per call (like the graph user), so German answers get German news and a German-rendered page. Search-engine requests carry a full Chrome header set with a language-aware `Accept-Language` — a normal user request, not a bare script, and what makes German queries return German results. A walled or down source degrades to zero results without failing the search (DuckDuckGo intermittently rate-limits datacenter IPs, so its HTML fetch retries once); measured per-engine availability from server IPs is in `DEPLOYMENT.md`. A fully failed search degrades to a normal answer and is reported in the backend logs (`websearch_success` / `websearch_failure` / `websearch_skipped` for the up-front search, `websearch_tool` for the brain's tool calls). Needs outbound internet from the backend container. The brain's system prompt also carries each server's state per request, so it knows when web search is on or off and answers capability questions ("can you search the web?", "is the MCP server available?") about the feature instead of denying it — and while it is off, it is told that live data (the weather now, news, prices, scores) needs the **MCP web search** toggle enabled, so it answers a weather question honestly instead of guessing.
- **Stop the answer by voice.** While an answer is being spoken, a parallel wake watch probes the microphone with the same trailing-edge trigger as the wake probes (350 ms of silence, plus a forced probe after 3 s of unbroken voice, because the speaker echo keeps the mic active) — so a stop command cuts the speech within at most 3 seconds of being said, for every voice profile. Saying the wake word plus a stop word ("stop", "stopp", "stop it", "halt", "still", "quiet", "enough", "genug", "genugsam", "das reicht", "reicht", "schweig", "schweigen", "hör auf", "lass es", "lass das", "genug schon") cuts the speech: the Live log says so, the pipeline beeps and returns to wake listening without a brain round trip. Saying **just the stop word, without the wake word**, also cuts the speech — that is the escape hatch for answers that run too long. With speaker echo the probe window transcribes as the answer's own words plus the stop word, so the match is echo-aware: it fires when the whole window is the stop word, or when the stop word stands alone (word boundary, anywhere in the window) **and** the window's audio carries a loud user burst — a contiguous ≥200 ms run of mic blocks at least 1.5× the window's voice-block median, i.e. the user's own voice standing out against the quieter echo. A pure-echo window (no user burst) can never self-trigger on an answer that merely ends on a stop word, and a stop word buried in the echo's text without the user's voice is ignored. The same echo-aware rule applies to the wake pipeline's fallback: the same stop word heard up to 10 s after the speech already finished is treated identically, wake word or not (the fallback's permissive match additionally requires the stop word to end the utterance). Every watch probe's transcript lands in the Live log ("Speech watch probe: …"), so a stop that does not trigger is debuggable from the page alone. Any other command heard while speaking ("Rocky, what time is it?") cuts the speech and starts a new brain round trip with it.
- **Text-only mode.** The **Speak / Text only** switch in the voice settings turns spoken answers off: the answer is written to the Answer panel and the TTS step is marked skipped. The wake pipeline itself keeps running; the setting is saved per browser.
- Spoken output is plain language only: before any TTS request or `speechSynthesis` utterance, markdown, links, code markers, URLs and special signs are stripped (`textForSpeech` in `public/voice.js`). The printed Answer panel keeps the brain's text verbatim.
- **Knowledge graph (MCP + panel).** Next to web search there is a second MCP server, **Knowledge graph** (`id: "graph"`), giving the brain read-only access to the Neo4j knowledge graph through our own `mcp/graph.mjs` (Node stdio, spawned by the backend exactly like the web-search server). With the toggle on, the brain's system prompt carries the user's own stored entities (a bounded context block, owner-scoped — there is no shared tier), and the brain can call four parameterized read tools — `get-schema`, `get-entity`, `list-my-knowledge`, `list-my-facts` — over up to five tool rounds within the request deadline; there is no Cypher tool at all, so a prompt-injected brain cannot write or read outside the injected user's scope. The brain's system prompt also carries a short data-model cheat-sheet (accounts are `:User` nodes, everything else is `:Entity` owned by the signed-in user, and a user's stored facts are the *outgoing relations* of their `:User` node, with an example query), so "what does X like?" is answered by querying the relations instead of just the node. The graph is populated automatically: after every answered turn the backend (never the brain) makes one structured extraction call over the prompt, the web search results and the answer, and upserts the entities and relations — the app's only write path, run fire-and-forget so the spoken reply is never blocked. A normal chat turn can never write to the graph: the user's own brain gets no write tool and there is no Cypher on the surface, so the write paths are the backend's own ingestion (only `MERGE`/`SET` upserts) plus the admin session's explicit write/delete tools (see Knowledge graph). The one delete path is explicit: the panel's Remove button (`DELETE /api/graph/entity`) removes the selected entity, owner-scoped to the session user (the admin may remove any entity) — never reachable from the brain (see "Knowledge graph (Neo4j)"). The **Knowledge graph panel** below the Prompt/Answer panels shows the signed-in user's world — node/link counts, a live 3D force layout of the newest (or a clicked node's) neighbourhood (three.js, animated, drag-to-orbit and wheel zoom, link labels with the relation type in plain words; a static 2D SVG toggle is available, and browsers without WebGL 2 fall back to it automatically; two sliders under the panel head — **Entities** for the node size and node names, **Link text** for the edge labels — scale both views live from 50% to 200% and are saved per browser), the schema, and recent activity (the brain's read queries, ingested turns and explicit removals); it refreshes every 15 s and after each answered turn. Without the `NEO4J_*` environment variables everything degrades to "not configured" (panel status line, no tools, the brain is told the feature is unavailable) and nothing else changes. The panel head's **Full view ↗** link opens the same two renderers full-size in its own tab (`/graph.html`), with a server-side fuzzy search over the whole graph (index-backed, typo- and case-tolerant), single-hit camera centring, the signed-in account in the head bar and per-view slider sizes (see "Knowledge graph (Neo4j)" → Full-size graph page).
- **Multi-user login**: the shell opens on a sign-in form (users from `USERS`, default `Mila,Roman`; each user's password is their own name). A successful login sets an HttpOnly session cookie; every `/api/*` route (except login/logout/health) requires it and answers 403 otherwise, which the UI turns back into the login screen. (403, deliberately not 401: the app sits behind the gateway's Basic Auth layer, and a 401 arriving on a request that carried those credentials makes the browser clear its cached Basic credentials and prompt again — see `DEPLOYMENT.md`, "Double Basic Auth prompt".) Each user's prompt history is kept on the server **per account**, so Mila and Roman have completely separate prompt caches (shared across that user's own tabs) with no connection between users. Sign out from the hero or just close the tab (sessions live 7 days, in memory only).

## Browser limitations

**Arm Jarvis sends voice-containing wake probes to your configured Whisper server even before a wake phrase is detected.** It is server-side wake detection, not a local/private wake-word model. Silent windows are not uploaded. A bounded 45-second PCM buffer stays in browser memory; the backend does not save recordings.

Keep the HTTPS page in the foreground. Hiding it explicitly stops the microphone, speech output and pending requests; return and click **Arm Jarvis** again. Microphone denial or interrupted capture is shown as an error. Wake response time includes a roughly two-second probe interval plus Whisper latency. This consumes server inference capacity while armed; an on-device wake engine would be a future alternative, not a feature of this build.

The reactor and active pipeline step follow the actual operation, not independent display timers. The hero heading next to the animation shows the stage name and a short caption about what is running — never endpoint URLs, host names, payload sizes or request IDs. Those appear **in the Live log and the Pipeline panel's status line only**; an error's detail (for example the failing Whisper host) stays there too, and the hero just says "Something went wrong. See the Live log for details." Only one pipeline runs per tab. **Stop** invalidates all callbacks, aborts requests, releases tracks and cancels TTS; **typing a prompt directly in the Prompt panel** (Send) is available only when disarmed. Disarming resets every pipeline step to waiting, so a finished or interrupted run — including the direct-prompt flow, whose brain and speech-output steps complete while disarmed — never leaves green done, gray skipped or red error icons behind.

Layout: the **Prompt/Answer** panels sit at the top (each tall enough to hold a full answer, and the Prompt panel carries the direct prompt input). A **Panels off/on** switch below them hides or shows everything underneath — refused while a session runs, because the Stop button lives in the hidden area. Under the switch: the **Mic level** panel holds both meters — the live mic bar and the green **Silence** bar, each with its own value readout (the silence bar fills live during wake listening, so speaking the wake word is visible) — both bars run on a dedicated 100 ms timer independent of the pipeline loop, so they keep filling in real time while audio is in flight to Whisper or the brain instead of freezing and jumping when the round trip returns — plus the **Silence stop** slider (100 ms-5 s) that sets the command's silence stop point, live and per browser — the **Pipeline** panel sits directly below it, and the main controls row (Arm Jarvis, Stop, language switch and the per-server **MCP** switches, all in one row) comes after them. The **Live log** is a full-width panel at the very bottom of the page.

Set **Your wake word** and click **Apply wake word** to override the server default (`Hey Rocky`) for your browser. Applying stops any active session; click **Arm Jarvis** again. The setting is saved in local storage per browser profile and website origin (the NBG and VIE URLs have separate settings), not shared with other users. Use 1-60 characters: words/numbers, spaces, hyphens or apostrophes. If storage is blocked, the UI explicitly reports that the change applies only until reload.

The **Live log** prints `Wake probe recognized: "..."` and `Command recognized: "..."` for Whisper responses, including non-wake speech. Empty responses show `(no speech recognized)`. Endpoint, request ID and attempt metadata follow separately. These readable transcripts are displayed in this tab, not added to persistent Docker logs; Clear removes the visible log.

Commands end after the silence stop (server default `SILENCE_MS`, overridden per browser by the Silence stop slider, 100 ms-5 s) of silence, with a 10-second wait for initial speech and a 15-second command limit. Whisper upstream requests time out after 20 seconds per endpoint and brain requests after 45 seconds. TTS has a bounded watchdog that cancels speech and reports an error rather than pretending playback finished.

## Answer voice

Pick **Answer voice** in the UI; the choice is saved in local storage per browser profile and origin, like the wake word, and applies to the next answer. An answer that is already being spoken finishes in the old voice.

**Speaking speed** is a slider from 0.60x to 1.60x, also saved per browser. It is a multiplier on the chosen voice's own pace, so 1.00x is the voice as designed; it scales the `speed` sent to the TTS engine and the `speechSynthesis` rate alike, clamped to the 0.5-2.0 both accept.

**Speak / Text only** (in the same settings block) turns spoken answers off: the answer is written to the Answer panel as text only and the pipeline's TTS step is marked skipped. The microphone and wake listening keep running. Saved per browser; while off, the voice select and speed slider are disabled.

- **Browser voice** — unchanged `speechSynthesis` behaviour, one utterance per answer, no backend needed.
- **HAL 9000** — the answer is split into clauses on sentence punctuation. Each clause is synthesized by the TTS endpoints in `TTS_ENDPOINTS` (requested at `speed` 0.8), then played through a Web Audio chain that band-limits it to roughly 95-3800 Hz, lifts 220 Hz, compresses it flat and adds a short room tail, with a 420 ms pause between clauses. The next clause is fetched while the current one plays.
- **Character profiles** (Commander, Android, Wizard, Newscaster) — delivery styles rather than clones of specific people. Each is a distinct pace/pitch/clause-pause shape (see `voiceProfiles` in `public/voice.js`), and the backend maps each profile to its own Kokoro voice (`profileVoices` in `server.js`: Commander `bm_daniel`, Android `bm_lewis`, Wizard `bm_fable`, Newscaster `am_michael`; HAL 9000 stays `bm_george`). The timbre comes from the self-hosted Kokoro model, so these are "in the style of" an archetype, not recordings of any real actor. Without a TTS backend they fall back to `speechSynthesis` at their delivery shape.
- **Named male/female voices** — Heart, Bella, Nicole and Sarah (female; Kokoro `af_heart`, `af_bella`, `af_nicole`, `af_sarah`) and Adam, Eric and Liam (male; Kokoro `am_adam`, `am_eric`, `am_liam`). The Answer-voice select is grouped Basic / Character voices / Female voices / Male voices, so switching gender is a two-level choice and the stored value is still the flat profile id. Each named voice carries its own delivery shape and a browser-voice fallback that matches its gender (the `speechSynthesis` picker boosts voices of the profile's gender and penalizes the other; German mode picks a female German voice for female profiles and a male one by default).

`TTS_ENDPOINTS` must speak the OpenAI `/v1/audio/speech` protocol. The deployed backend is the `speaches` container on gpu-1, which serves both `/v1/audio/speech` (Kokoro) and `/v1/audio/transcriptions` (Whisper large-v3) behind one API key — see `DEPLOYMENT.md`. Kokoro-FastAPI and openedai-speech (which can front Piper) are drop-in alternatives. The browser only talks to `/api/speak` on this backend, so `TTS_API_KEY` stays on the host.

Multiple endpoints are comma-separated and tried round-robin with failover, like Whisper. Each clause request times out after 20 seconds. Measured against gpu-1 over HTTPS: about 0.5 s per clause for synthesis and 1.0 s for a short command transcription.

**Answer text is sent to the configured TTS endpoints.** `/api/speak` truncates at 2000 characters and clamps speed to 0.5-2.

With `TTS_ENDPOINTS` empty, HAL 9000 is still selectable but degrades to `speechSynthesis` at rate 0.68 and pitch 0.5, preferring a deep English voice if the browser has one: the cadence survives, the filtering and reverb do not. The same fallback finishes the remaining clauses if the TTS backend fails part-way through an answer, and the live log says so rather than dropping the rest of the answer.

## Language switch (English / Deutsch)

The **Language** toggle in the controls row (a single sliding switch next to Arm Jarvis / Stop) sets the spoken language for the whole pipeline at once, per browser (saved in local storage, like the wake word). **English is the default** when a browser has not saved a choice, regardless of the server's `WHISPER_LANGUAGE`:

- **Whisper** — each probe and command request sends the language to the STT endpoint (`/api/transcribe?language=de`); the server default is `WHISPER_LANGUAGE`.
- **Brain** — each `/api/chat` request carries the language and the backend appends a `Language override: answer in …` directive to the system prompt, which wins over a hardcoded language in `BRAIN_SYSTEM_PROMPT`.
- **Spoken output** — English keeps the selected profile's behaviour (neural TTS first). **German uses the browser voice with a German voice** (male preferred when the browser has one), because the self-hosted Kokoro engine on gpu-1 ships English voices only. The live log says so when it kicks in.

The switch applies live from the next request and does not stop a running session; an answer already being spoken finishes in its original language.

## Login (multi-user)

The app opens on a sign-in form. Users come from the `USERS` environment variable (comma-separated, default `Mila,Roman,admin`); **each user's password is their own name** — Mila signs in with username `Mila` and password `Mila`, Roman with `Roman`/`Roman`, the admin with `admin`/`admin`. User names are matched case-insensitively; the password must equal the name.

- **The admin account** (`ADMIN_USERS`, default `admin`) is a subset of `USERS`: it signs in exactly like any other user and gets the admin session — the global knowledge-graph panel (every user's data), the global activity feed, the brain's cross-owner read tools, and the brain's admin write/delete tools (see Knowledge graph). A name in `ADMIN_USERS` that is not in `USERS` simply cannot log in.
- A successful login creates an in-memory server session (random 256-bit token) and sets it as an `HttpOnly; SameSite=Lax` cookie (`Secure` when the request arrives through an HTTPS front). Sessions live 7 days and die with a server restart, like all prompt history.
- **Every `/api/*` route requires the cookie** (except `/api/login`, `/api/logout` and the public `/api/health` used by the container healthcheck) and answers `403` otherwise. The UI treats the 403 on `/api/config` as "show the login screen", so no API data ever reaches a signed-out tab. A wrong username or password also gets 403 (the 429 lockout is unchanged). The app never answers 401: behind the gateway's Basic Auth layer a 401 makes the browser drop the cached mesh credentials and re-prompt Basic Auth on the next request.
- **Per-user prompt caches**: the conversation history behind the brain is keyed by the authenticated account, not by a browser tab. Every tab signed in as Mila shares Mila's last-10-messages cache; Roman's cache is a different entry the server never mixes with it. There is no route or payload by which one user can read or influence the other's session — the client-sent session id is ignored.
- **Jarvis knows who is signed in.** The brain's system prompt carries the authenticated user's name and is told it is their first name, so answers address the user by name (Mila gets "Mila, …", Roman gets "Roman, …").
- **The brain answers as the wake word's name.** Every brain request carries the active wake phrase (the server default, or the personal per-browser override), and the server derives the name from it — the phrase without a leading "Hey/Hi/Hallo" filler, capitalized: "Hey Rocky" → Rocky, "Kaya" → Kaya. The system prompt tells the brain its name is that word, so "Who are you?" gets "My name is Rocky, Mila." Browsers that send no phrase fall back to Jarvis.
- Five failed logins from one address lock it out for 15 minutes (429).
- **Sign out** (hero, next to "Signed in as …") stops any running session and deletes the server session; the cookie is cleared in the browser.

## Knowledge graph (Neo4j)

The knowledge graph is a Neo4j Community database on the compose network that stores what the assistant learns from conversations and web searches. **Every `:Entity` is private to its owner:** entities are keyed by `(name, owner)` — the name **case-insensitively**, the type is a property of the first stored copy, not part of the identity — with `owner` = the signed-in user of the turn that mentioned them, so the same thing mentioned by two users is two separate nodes ("Lego" mentioned by Mila and by Roman is `Lego(owner: Mila)` and `Lego(owner: Roman)`), but the same thing re-mentioned by one user with a different extracted type or casing ("BTCUSD" as `topic` then as `thing`) stays **one** node. There is no shared or public tier — no `common` flag, no `(:User)-[:KNOWS]->(:Entity)` bookkeeping edge: ownership *is* the provenance, and every read path (panel, brain context, brain tools) is pinned to `owner = $user`, so a user's world is bounded by construction. Facts are the relation edges: a core set of known types (`WORKS_AT`, `LIVES_IN`, `STUDIES_AT`, `BORN_IN`, `FRIEND_OF`, `FAMILY_OF`, `PART_OF`, `LOCATED_IN`, `RELATED_TO`, `MENTIONED_IN`, `LIKES`, `WENT_TO`, `OWNS`, `USES`, `INTERESTED_IN`, `WATCHES`) plus relation types the extraction **introduces** for a relation none of them expresses (the prompt prefers the known types and may coin a short UPPER_SNAKE_CASE type for a genuinely different relation — "I'm interested in X" → `INTERESTED_IN`; Neo4j creates the type on first use, and the schema, the panel labels and the brain's fact formatting are all type-agnostic, so a new type shows up everywhere immediately; a malformed "type" that is really prose falls back to `RELATED_TO` so the fact itself is never lost, and the bookkeeping `KNOWS` is never emittable). Save/track instructions are extracted like statements: "add X, Y to my (trading) news list" / "remember these topics: X, Y" store a `WATCHES` fact from the user to each listed topic (so the brain later finds the user's trading news list in the graph and fetches news for each topic with `web_news`), and assigning a topic to a **named list** ("assign X to my TradingMonitor list") stores the list itself as an entity (type `thing`, the exact name the user gave it) plus a `PART_OF` membership edge from the topic to the list — so the list appears as its own node in the graph panel, with its members attached, and a "news about my TradingMonitor list" question resolves the members and fetches each with `web_news`. The brain is told in its system prompt that the graph updates automatically after every answer — so it confirms such requests instead of claiming it cannot write (the admin session is the exception: its turns are not ingested — it is a service account for graph maintenance that changes the graph only through its explicit write tools, so its conversations never mint `owner=admin` copies of other users' entities). Every relation can carry a `negative` flag — negation is a property of the relation, never a separate type ("I don't like X" is `LIKES` + `negative`) — and since ingestion upserts with `SET`, a later statement flips the same edge instead of adding a second one. Every registered user is a single node: the `:User` account *is* the person — the extractor lists people as person entities, but ingestion never stores an entity named after a registered user (that would be a second, same-named `:Entity`, i.e. a proxy for that user's personal data), and relations named after any registered user (`Mila -LIKES-> Lego`, stated by or about Mila) attach to that user's `:User` node. The only exception to per-user visibility is the administrator, which comes in two forms: the **admin login** (a normal user in `USERS`, listed in `ADMIN_USERS`, default `admin`/`admin`) whose panel shows the whole graph, whose brain tools read across all owners, and whose activity feed is global — and **direct database access** (`neo4j-admin` / `cypher-shell` on the `neo4j` volume) to query across all owners (`MATCH (e:Entity {name: "Lego"})` returns every owner's copy). The per-user guarantee is enforced by the application layer, not by the database (Community Edition has no RBAC), so treat the database credentials — and the admin account — as full access to every user's data.

**Per-user data isolation.** Everything the graph stores is private to its owner: an `:Entity` belongs to exactly one user (`owner`), and a fact edge is visible to a user only when every `:Entity` endpoint of the edge is theirs. `:User` nodes are account markers (name only, no personal data) and may appear as fact-edge endpoints in the owner's panel — e.g. a fact Roman states *about* Mila (`Mila -LIKES-> Pizza`, where Pizza is Roman's copy) shows in Roman's panel with Mila's type-less account node, and a pure user-to-user edge is visible only to its two parties. Nothing else crosses the boundary: the panel, the activity feed, the brain's context and the brain's tools are all scoped to the signed-in session user:

- The panel (`/api/graph/status`, `/api/graph/subgraph`) shows the signed-in user's drawn world only — their `:User` node, the entities they own, and the fact edges between them (ownership bounds the world; there is no neighbour expansion to leak through). An *isolated mention* — an entity the user owns but no visible fact edge touches — is drawn **dimmed** (the node carries an `isolated` flag that both views render with reduced opacity): what the brain's `list-my-knowledge` reports is exactly what the panel shows, just visually marked as "known, nothing stored about it". With a `center`: a *visible* centre (the user's own node or an entity they own — an isolated one included, returning just itself) plus its neighbours (their own entities and `:User` account markers; a centre the user cannot see comes back empty). Another user's entity or fact edge never appears, no matter which `center` elementId the client sends. The activity feed lists only the session user's own brain reads and ingested turns — an ingest entry counts what the write actually *stored*, so a turn that only mentioned a registered user (whose name is that user's account node, never an entity) reads "N user-account mentions — nothing stored as an entity", not "stored N entities". **The admin session is the exception**: its panel shows the whole graph — every user's account node, every owner-keyed entity (same-named copies of different owners labelled with the owner) and every fact edge — and its activity feed is global.
- The brain gets four **parameterized** read tools — `get-schema`, `get-entity(name)`, `list-my-knowledge`, `list-my-facts(about?, relation?)` — and no Cypher at all. The backend injects the session `user` into every call (the tool schema the brain sees has no `user` parameter), and every query is built server-side inside `mcp/graph.mjs`, pinned to `owner = $user` (entity lookups) or the user's `:User` node (facts). A foreign or unknown entity name returns exactly the same "no entity" answer as a nonexistent one — there is nothing to enumerate. The brain is told in its prompt that the graph is this user's private world with no shared tier, so "what does Mila like?" asked by Roman gets "no stored information", and the queries make it impossible to answer otherwise. The prompt also requires the brain to phrase anything it says about the graph from the signed-in user's private view ("I have no record of you liking X", "I have no access to other users' facts") — never as a global claim about the whole graph ("no one likes X") — so a scoped answer is never misread as a statement about everyone's data. **The admin session is the exception**: the same four tool names then read across all owners (the backend injects `admin: true`, never the brain) — `get-entity` returns every owner's copy with its owner, `list-my-knowledge` lists every user's entities grouped per user, `list-my-facts` every user's facts — and the brain is told this is the admin session, where it may answer about any user's stored data but must attribute each item to its user. The admin brain additionally gets four **write/delete tools** — `store-entity(owner, name, type)`, `store-fact(owner, from, to, type, negative?)`, `rename-entity(owner, name, newName)` and `delete-entity(owner, name)` — offered to the brain only in the admin session: the backend injects `admin: true` and the registered user list per call (none of those parameters is in the tool schema the brain sees), and the MCP server re-checks the flag and the owner before any database access, refusing every other call. `owner` must be a registered user (so a write always lands under a real account's name — the cross-user reach is the point of the admin session), a user-named endpoint becomes that user's `:User` node, and `:User` nodes can never be deleted; every write/delete is audited in the global activity feed. A rename is an in-place name-property change — the node keeps its elementId, its type and **every link** (a delete+recreate would detach them), and it is refused when the new name is a case-variant of the current one, a registered user's name, or already taken by that user's other entity copy.
- Ingestion keeps the invariant: entities are upserted keyed by `(name, owner)` (the name case-insensitively — a different extracted type or casing never creates a second copy; the first stored copy's spelling and type is kept) — one node per owner per entity — entities named after a registered user are dropped, and relation endpoints named after a registered user resolve to that user's `:User` node (the node is `MERGE`d if it does not exist yet), while entity endpoints resolve to the turn user's own copies (`owner: $user`) — so a fact about a user is stored *on* that user, and a fact between two of a user's entities stays inside their world.

**A normal chat turn can never write to the graph, and can never read another user's data.** Neo4j Community Edition has no roles or grants — RBAC (`CREATE ROLE`, `GRANT`) is Enterprise-only, and every Community user has implied admin privileges (verified on `5.26.31`: the server rejects `CREATE ROLE` with `UnsupportedAdministrationCommand`). So the guarantees are enforced by the MCP server and the application layer, not by the database:

1. The brain's graph MCP server is our own (`mcp/graph.mjs`, Node, stdio, spawned by the backend with the read-only `jarvis_read` credentials; it opens a second driver with the `jarvis_write` credentials only for the admin write tools). It exposes the four parameterized read tools above — plus the four admin write/delete tools, refused on every call that does not carry the backend-injected admin flag — and **no Cypher at all** — not even a read-Cypher tool. With no free-form query on the surface, a prompt-injected brain cannot run `CREATE`/`MERGE`/`DELETE` and cannot construct a query that reaches outside the injected user's scope: every query string lives in `mcp/graph.mjs`, and every read is pinned to the `user` argument the backend injects (a call without it fails, defense in depth).
2. For a normal user the only write path is the backend's own turn ingestion, after the answer is already delivered: one cheap structured LLM call extracts entities and relations from the prompt, the web search results (if any) and the answer, and the result is sanitised (allowlisted entity types and relation types, capped counts, validated property keys, boolean negation flag) and upserted with `MERGE`/`SET` using the `jarvis_write` user — there is no `DELETE` anywhere in the ingestion code. A failed extraction is skipped, never a crash and never a partial write.
 3. The delete paths are **explicit and bounded, never free brain choice**: `DELETE /api/graph/entity?id=` (the panel's Remove button on the selected node) matches `:Entity` only, pinned to `elementId(e) = $id AND e.owner = $user` — a foreign or already-removed id 404s exactly like a nonexistent one, and a `:User` account node can never match. The admin session may delete any entity (no owner pin) either through that endpoint or its `delete-entity` tool, which is owner-validated (registered users only), matches `:Entity` only, and can never touch a `:User` account node. Each removal is recorded in the activity feed as an audit entry.

**The admin session is the one write-capable brain**, and it is gated twice: the backend offers the write/delete tools only to the admin session and injects the `admin` flag and the registered user list per call (a chat turn — or a prompt injection riding on it — can never set them, they are not in the tool schema), and the MCP server re-validates the flag, the owner and the arguments before any database access, so a forged or non-admin call is refused before the write driver is even reached. The admin's writes use the same semantics as ingestion (entities keyed by `(name, owner)`, the name case-insensitively, user-named endpoints become `:User` nodes) and go over the `jarvis_write` credentials.

The `jarvis_read` and `jarvis_write` database users exist for credential separation (MCP/panel reads vs ingestion and admin MCP writes); Community Edition does not restrict what either user can do at the database level, so treat both passwords as write access to the graph.

**Panel.** The Knowledge graph panel below the Prompt/Answer panels (always visible, like the transcript) is scoped to the signed-in user: node/link counts, a live 3D view of the newest subgraph (the default — a continuously animating three.js force layout with drag-to-orbit, wheel zoom, click-to-re-centre, and labels projected over the canvas), plus a static 2D SVG toggle with the same click-to-re-centre behaviour. Every link carries its relation as a plain-word label in both views, with the negative form where the fact is negated (`LIKES` → likes, `LIKES` + negative → doesn't like, `LIVES_IN` → lives in — the label map is `public/relLabel.js`), so the graph reads like sentences together with the node labels (Mila —likes→ Lego); parallel edges on the same pair stack their labels. Only real facts are drawn, and the only nodes that can appear are the user's own `:User` node, the entities they own, and `:User` account markers at the endpoints of those edges — another user's entity is unreachable by construction (the panel queries match on `owner`). Every entity in the world is drawn — including an *isolated mention* (an entity the user owns but no fact edge touches), which both views render **dimmed** (the node carries an `isolated` flag): what the brain's `list-my-knowledge` reports is exactly what the panel shows, just visually marked as "known, nothing stored about it". Selecting an entity (clicking its node) offers the **Remove** button — the panel's explicit delete path: a confirmation, then `DELETE /api/graph/entity` pinned to the session user's own entities (`:User` account nodes are never offered; the admin may remove any entity, whose copies carry the owner suffix) — and each removal is audited in the activity feed. three.js is vendored locally (`public/vendor/three.module.min.js`, pinned `0.164.1`, no CDN at runtime) and the 3D view needs WebGL 2 — browsers without it fall back to the 2D view automatically (the 3D toggle is disabled). Two size sliders under the panel head — **Entities** (node size and node names) and **Link text** (edge labels) — scale the 2D and 3D views live from 50% to 200%: the 2D node radius and name font are drawn from the scale at render time (the layout is deterministic, so re-rendering on slider input does not move nodes), the 3D spheres rescale in place (the settled layout keeps its positions) and the 3D labels plus both views' edge labels read the scales as CSS custom properties, so a slider drag updates the open view without any rebuild; the values persist per browser (local storage) like the other per-browser settings. The schema and recent activity — the signed-in user's own brain reads and ingested turns, with a short tool/argument summary instead of raw Cypher (there is none on the brain's surface) — double as the audit trail that only reads ever come from the brain. The `:User` node is drawn larger, in the accent colour and labelled `(you)` — it is the only node of the signed-in user that can appear, so the account is never confused with anyone else's data. Endpoints: `GET /api/graph/status`, `/api/graph/subgraph?limit=&center=`, `/api/graph/schema`, `/api/graph/activity`, `GET /api/graph/search?q=&limit=` (the full-size page's search, all read-only) and `DELETE /api/graph/entity?id=` (the Remove button), all session-gated like the other `/api` routes and scoped to the session user (the delete owner-scoped as above).

**Full-size graph page.** The panel head's **Full view ↗** link opens `/graph.html` in its own tab: the same two renderers (3D default, 2D SVG toggle) filling the viewport, with larger defaults — the entity/link-text sliders start at 150% and persist under their own storage key (`jarvis.graphSizes.full`), so the panel's sizes are untouched. The head bar shows the node/link counts, a chip with the **signed-in account** (the admin sees the whole graph, so same-named copies carry the owner in their labels), the 3D/2D toggle, the two sliders, a Refresh button (clears the selected neighbourhood) and a back link; below it the search row and a hint line, and the stage takes the rest of the viewport height (head, search and hint take their natural size, the stage shrinks instead of pushing them off-screen — regression-tested at phone through desktop sizes). **Search** runs on the server against the whole graph, not just the drawn window: a Neo4j full-text (Lucene) index over `(name, owner)` (created idempotently at startup by `ensureIndexes()`, together with the owner/last-seen indexes the panel reads need) answers each query in index time, so it stays usable at millions of nodes. The query text is data — Lucene special characters are escaped before they reach the index — and every token must match (AND); within a token the exact term outranks a prefix, which outranks a fuzzy (typo) match, with the edit-distance budget growing with token length (none on 3 letters, one up to 5, two beyond), so "nvi" finds Nvidia and "nvidea" forgives the swap. Relation types cannot go in a node index, so they are matched in JS against the bounded type list from the token store (every token must hit one of the type's words — "interested in" and "interest" both find `INTERESTED_IN` — and the reserved `KNOWS` bookkeeping type is never emittable). The owner is a REQUIRED Lucene term for a non-admin session (re-checked server-side after the index), pushing the per-user boundary into the index instead of filtering a global top-N afterwards; the admin searches the whole graph. Results are paged (`limit`, one row fetched beyond it so the UI can say the list was cut), and the drawn view is never paged — that is what keeps the page usable on a huge graph: the drawing only ever shows a bounded window (60 nodes). Typing highlights every hit that is in the drawn window in both views (everything else fades to 0.1 opacity / dimmed labels, edge labels included) so the search reads as a filter on the picture. Narrowing the query to **exactly one entity** additionally moves the 3D camera onto it, live: `setFocus()` in `public/graph3d.js` re-reads the node's position every frame (the force layout keeps moving it, so the follow is per-frame, not a one-off recentre) — a lone hit outside the drawn window is fetched first (its neighbourhood subgraph, guarded so re-typing the same query does not refetch), and picking a result from the paged list does the same and keeps the hit highlighted there. Clearing the search — deleting the text, the input's X, the Clear button or Escape — lifts the highlight, and if the search had swapped the drawn window to a neighbourhood it restores the initial objects (and resets the centre, so the 15 s poll stops re-fetching the neighbourhood); a window the user chose by clicking a node in the drawing persists until Refresh, as in the panel. A signed-out tab gets the app's 403 on `/api/config` and shows a sign-in hint instead of a graph.

**Running without a graph.** Leave the `NEO4J_*` variables in `.env` empty: the endpoints answer `503 graph_not_configured`, the panel shows "Not configured on this server", the brain is told the feature is off, and chat behaves exactly as before.

## Troubleshooting

**"I say the wake word and nothing happens."** Three causes have actually been observed, in
descending order of likelihood:

1. **The microphone never goes quiet.** A command is only submitted after the silence
   stop (default `SILENCE_MS`, 1.5 s; adjustable 100 ms-5 s with the Silence stop
   slider) of silence; if the room noise floor stays above the capture threshold
   (`0.012` in `public/audio.js`), recording runs to the 15-second cap instead, then
   uploads a window that is mostly noise and comes back empty. The **Listening for
   command** stage counts elapsed time and shows the live mic level while it waits, so
   watch those: if the level never falls near zero, lower the input gain or raise the
   threshold. (A longer silence stop helps only if the noise is bursty; a steady noise
   floor needs gain/threshold work.)
2. **Language mismatch.** `WHISPER_LANGUAGE` is `en`. German speech forced through the
   English model is mangled badly enough that the wake phrase no longer matches:
   *"Rocky, wie viel Uhr ist es?"* came back from the live service as
   *"Roki waivil ua ist iz."*, so the pipeline never starts. Speak the configured
    language, flip the **Language** switch (it sends the language with every probe),
    or change `WHISPER_LANGUAGE`.
3. **Saying the wake phrase alone** opens the two-step flow: a beep, then up to 10 s
   waiting for a separate command. Saying phrase and command in one breath
   ("Rocky, what time is it?") skips it.

**Phantom answers.** `large-v3` emits `"Thank you."`, `"Okay."` or `"You"` for
near-silence even with the VAD filter on, so those exact strings are filtered as
hallucinations alongside the ZDF/Amara subtitle artefacts. Without the filter, a silent
command window would send a phantom prompt to the brain.

Keep `WHISPER_VAD_FILTER=true`. It is what suppresses those hallucinations: with the
filter off, pure digital silence transcribes as `"Thank you."` every time. It does not
cost sensitivity, as speech 3% of full scale still transcribed correctly in testing.

environment signal, not a regression; verify on a host where
